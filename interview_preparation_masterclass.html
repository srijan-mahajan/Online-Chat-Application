1. Project Description (Pitching to Interviewers)

"I developed a secure, real-time collaboration application called NexusChat. The system features a responsive, event-driven frontend built with Vanilla HTML5, CSS3 (Glassmorphism design), and JavaScript. The backend is powered by Spring Boot (Java 22) running raw WebSockets for bi-directional communication, and using JSON Web Tokens (JWT) alongside BCrypt encryption to secure user sessions. I integrated a cloud-hosted MongoDB Atlas database for persistent message logs, lazy-loaded history retrieval, and user status indicators."

3. Spring Boot Concepts
Q: Why Spring Boot? Why not Spring MVC only? What problems does Spring Boot solve?
Answer

Spring MVC requires complex XML configurations, manual servlet mappings, and explicit dependency management. Spring Boot solves these problems by offering Starter Dependencies (which group libraries together), Auto-Configuration (which configures beans automatically based on the classpath), and an Embedded Tomcat Server, making applications running-ready out of the box.

Q: Explain Auto-Configuration and Dependency Injection.
Answer

Auto-Configuration scans the project libraries on startup and dynamically registers beans (e.g. if `spring-boot-starter-data-mongodb` is present, it auto-configures `MongoTemplate`). Dependency Injection (DI) is a design pattern where the framework provides dependent objects rather than the class creating them itself, yielding loose coupling.

Q: What is the difference between @Component, @Service, @Repository, @Controller, and @RestController?
Answer

- @Component: The generic stereotype annotation for any Spring-managed component (bean).
- @Service: Specializes @Component, representing domain business logic.
- @Repository: Specializes @Component, representing the database access layer; translates database exceptions.
- @Controller: Renders server-side HTML/web views.
- @RestController: Combines `@Controller` and `@ResponseBody`. It indicates that methods return domain objects serialized directly into HTTP response bodies (JSON).

Q: Why constructor injection instead of field injection (@Autowired)?
Answer

Constructor injection enforces immutability (fields can be declared `final`), prevents partial initialization, makes the class independent of the Spring container during unit testing, and highlights circular dependencies on compilation.

Q: Explain the Spring Bean Lifecycle, IoC (Inversion of Control), and ApplicationContext.
Answer

IoC is the framework design principle where the control of object creation is delegated to the container. The **ApplicationContext** is the IoC Container managing bean lifecycles. A **Bean Lifecycle** follows: Instantiate → Populate Properties → BeanNameAware/BeanFactoryAware → Pre-Initialization (`BeanPostProcessor`) → PostConstruct (`@PostConstruct`) → Initialization (InitializingBean) → Ready for Use → Pre-Destroy (`@PreDestroy`) → Destruction.

4. REST APIs
Q: Why REST? Compare REST and SOAP.
Answer

REST (Representational State Transfer) is a stateless, lightweight architectural style utilizing HTTP standards, returning payloads in JSON. SOAP (Simple Object Access Protocol) is a strict, XML-based protocol requiring strict WSDL contracts, adding message overhead.

Q: Difference between GET, POST, PUT, DELETE, PATCH. Explain Idempotency.
Answer

- GET: Retrieves a resource. (Idempotent: Yes)
- POST: Creates a new resource. (Idempotent: No)
- PUT: Replaces an entire resource. (Idempotent: Yes)
- PATCH: Partially updates a resource. (Idempotent: No/Yes depending on implementation)
- DELETE: Removes a resource. (Idempotent: Yes)
* **Idempotency** means running the identical API request multiple times produces the same system state as running it once.

Q: Why should GET never modify data? Why plural resource names?
Answer

GET requests are cached by browsers and proxies. If a GET request changes data, intermediate caches or crawler pre-fetching will trigger state changes, violating safety specifications. Plural resource names (e.g. `/messages` instead of `/message`) are a RESTful best practice because they represent the collection of resources.

5. Controller Layer
Q: Why not write business logic in the Controller? How does a request reach the Controller?
Answer

Controllers should only handle HTTP concerns (parsing input, HTTP status codes). Business logic belongs in the Service layer to allow reusability and isolated unit testing. The request reaches the Controller via the **DispatcherServlet**, which is the front controller matching incoming URLs to handler method mappings using a HandlerMapping configuration.

Q: Difference between @RequestBody, @PathVariable, @RequestParam, and @RequestHeader.
Answer

- @RequestBody: Deserializes the JSON body of an HTTP request into a Java object.
- @PathVariable: Extracts values from the URI path template (e.g. `/messages/{id}`).
- @RequestParam: Extracts query parameters (e.g. `/messages?limit=10`).
- @RequestHeader: Accesses metadata properties from the HTTP request headers (e.g. `Authorization`).

6. Service Layer
Q: Why create a Service Layer? What if the Controller directly accesses the Repository?
Answer

If a Controller accesses repositories directly, it binds the HTTP transport layer to database structures, leading to code duplication. The Service Layer encapsulates transaction boundaries, business validation, caching, and coordinates multiple repository calls, enabling modular testing via mocking.

7. Repository Layer
Q: What is Spring Data MongoDB? How are repository methods implemented without writing queries?
Answer

Spring Data MongoDB is an abstraction layer that translates Java repository calls into BSON queries. By extending `MongoRepository`, Spring uses dynamic proxies at runtime to parse interface method names (e.g. `findByEmail`) and auto-generate the matching MongoDB database query under the hood.

8. MongoDB
Q: Compare SQL vs NoSQL. When should you NOT use MongoDB?
Answer

SQL is relational, structured, and strictly ACID compliant, which is perfect for ledger/banking systems. NoSQL (MongoDB) is document-oriented, scaling horizontally via sharding, which is perfect for write-heavy chat platforms. You should **not** use MongoDB when your schema requires complex multi-table transaction relationships (joins) that SQL foreign keys represent better.

Q: What is an ObjectId? What are Indexes, and why use them?
Answer

An **ObjectId** is a unique 12-byte identifier containing a timestamp, machine identifier, process ID, and a counter. **Indexes** are specialized data structures (B-Trees) that store a small fraction of the database collection's data in an ordered state. This allows MongoDB to scan indexes rapidly instead of executing slow collection scans on every query.

9. Authentication & JWT
Q: Explain the difference between Authentication and Authorization.
Answer

Authentication is validating *who* the user is (e.g., verifying their email and password). **Authorization** is validating *what* permissions they have once authenticated (e.g., check if they are authorized to read a specific private chat channel).

Q: Explain the complete JWT Authentication flow.
Answer
1. Client POSTs email/password to /api/auth/login. 2. Server validates password hash with BCrypt. 3. Server generates JWT (Header.Payload.Signature) signed with secret key. 4. Server returns JWT in response body to browser. 5. Browser saves JWT token in localStorage. 6. For future actions, browser appends 'token' parameter to WebSocket handshake URL. 7. Server Interceptor intercepts handshake, validates token, and approves socket connection.
Q: Compare JWT vs Session-based authentication. Where should JWT be stored?
Answer

JWT is stateless; the server stores nothing, saving memory. Session-based authentication is stateful, storing active session IDs in a server-side DB/RAM. For web security, storing JWTs in **HttpOnly Cookies** is the most secure method because it prevents Cross-Site Scripting (XSS) token theft. LocalStorage is easier to access via JS but vulnerable to XSS script injection.

Q: Why do JWTs expire? What is a Refresh Token? Can a JWT be hacked/revoked?
Answer

Since JWTs are stateless, they cannot be easily revoked by the server. If a token is stolen, the attacker has access until the token expires; thus, brief lifetimes (e.g. 1 hour) are used. A **Refresh Token** (stored securely in database records) is used to request new short-lived JWTs. To prevent hacking, JWT payloads must never contain sensitive details (like passwords) and should always be verified using HMAC-SHA signatures.

10. Spring Security
Q: What is the SecurityFilterChain, and why does a JWT filter extend OncePerRequestFilter?
Answer

The **SecurityFilterChain** is a chain of servlet filters that intercept, process, and secure incoming HTTP requests. A JWT filter extends `OncePerRequestFilter` to guarantee that the token validation logic executes **exactly once** per request, preventing redundant processing during internal servlet forwards or redirects.

11. BCrypt Password Hashing
Q: Why hash passwords? Can we decrypt a BCrypt hash? Compare Hashing, Encryption, and Encoding.
Answer

- **Hashing**: One-way transform. BCrypt hashes **cannot** be decrypted. Verification is done by hashing the attempt and comparing outputs.
- **Encryption**: Two-way transform using a key. Can be decrypted.
- **Encoding**: Data format translation (e.g. Base64) with no security key. Easily reversed.
* BCrypt is preferred over SHA-256 because it includes a "salt" (preventing rainbow table attacks) and is computationally slow, mitigating hardware-accelerated brute-force cracking.

12. Exception Handling
Q: How do you handle exceptions globally in Spring Boot?
Answer

I use **@ControllerAdvice** (or `@RestControllerAdvice`) to define a global interceptor class. Inside this class, I write methods annotated with **@ExceptionHandler** to catch specific exceptions (e.g. `BadCredentialsException`), mapping them to structured JSON payloads and returning clean HTTP status codes.

13. Input Validation
Q: How do you validate inputs in Spring Boot REST controllers?
Answer

By adding the `jakarta.validation` dependencies, we annotate DTO fields with validation rules like `@NotBlank`, `@Email`, and `@Size`. We then mark the DTO parameter in the controller method signature with **@Valid**. If validation fails, Spring throws a `MethodArgumentNotValidException`, which is caught by our global handler to return a 400 Bad Request status.

14. DTO (Data Transfer Objects)
Q: Why use DTOs? Why not expose the Database Entity directly?
Answer

Exposing database entities directly leaks database schema details, makes it hard to support API versioning, and opens the system to mass-assignment security vulnerabilities. DTOs act as a buffer layer, exposing only the exact fields required for a specific request or response payload.

15. File Upload & Safety
Q: How does file upload work? Why set a 5MB limit, and how do you prevent viruses?
Answer

- Files are sent as binary streams or Base64. A 5MB limit is set to prevent memory exhaustion on the server (which could lead to OutOfMemory errors).
- To prevent malicious uploads (like `.exe` scripts), the server must validate the file's **MIME type** (using magic bytes headers instead of checking only the file extension) and scan files using virus scanning software before writing them to disk.

16. Image Sharing
Q: Compare Base64 vs URL for image sharing in a real-time chat app.
Answer

Base64 converts image bytes into a text string that is sent directly through the WebSocket. This is simple and requires no extra infrastructure but increases the message size by ~33%. Using URLs is the professional standard: the image is uploaded via REST to cloud storage (like AWS S3) which returns a public URL link; only this lightweight link is sent over the WebSocket connection.

17. Frontend Design Decisions
Q: Why use Vanilla JS instead of React? How did you execute API calls?
Answer

Vanilla JS was chosen to eliminate setup complexity and allow clean integration with raw WebSocket APIs. I used the built-in **`fetch()`** API with `async/await` to handle asynchronous HTTP calls to our REST endpoints, parsing the responses to dynamically update the DOM tree.

18. CORS (Cross-Origin Resource Sharing)
Q: What is CORS? Why does the browser block requests? How is it resolved?
Answer

CORS is a browser-enforced security mechanism. By default, browsers prevent a webpage hosted on Origin A (e.g. `http://localhost:3000`) from making API calls to Origin B (e.g. `http://localhost:8081`). This prevents malicious scripts from making requests on your behalf. We resolve this by adding the `@CrossOrigin(origins = "*")` annotation in Spring Boot controllers, which adds the header `Access-Control-Allow-Origin: *` to the HTTP responses.

19. HTTP Status Codes
Q: List common HTTP Status Codes and which ones your application returns.
Answer

- **200 OK**: Returned on successful login.
- **201 Created**: Returned on successful registration.
- **400 Bad Request**: Returned if validation fails.
- **401 Unauthorized**: Returned if JWT verification fails.
- **403 Forbidden**: Returned if permissions check fails.
- **404 Not Found**: Returned if user search query has no matches.
- **500 Internal Server Error**: Returned on database errors.

20. JSON & Serializations
Q: How does Spring convert JSON payloads to Java objects?
Answer

Spring Boot utilizes the **Jackson library** by default. When an incoming JSON request reaches a `@RestController`, the `MappingJackson2HttpMessageConverter` deserializes the JSON string into the target Java object. For WebSockets, we manually configure and call Jackson's **`ObjectMapper`** to map strings into `ChatMessage` objects.

21. Real-Time Chat & Message Flow
Q: Compare WebSockets vs Polling, Long-Polling, and Server-Sent Events (SSE).
Answer

- **Polling**: Client repeatedly hits REST endpoints at fixed intervals. Inefficient.
- **Long-Polling**: Server holds the HTTP request open until a new message arrives. Still suffers from connection handshake overhead.
- **SSE**: Uni-directional push channel from server to client. Excellent for feeds, but cannot send client messages.
- **WebSockets**: Bi-directional, stateful full-duplex communication over a single TCP socket. The superior choice for chat apps.

22 & 23. Concurrency & Java Collections
Q: How do you handle race conditions when multiple users send messages simultaneously?
Answer

Spring WebSockets run asynchronously on a thread pool. To prevent data corruption, I used thread-safe collections: **`ConcurrentHashMap`** (for active socket mapping) and **`CopyOnWriteArraySet`** (for room membership sets). These implement lock-free read performance and thread-safe write isolation, preventing concurrency issues.

24 & 25. Java Concepts & OOP
Q: Explain where OOP concepts are used in your code.
Answer

- **Encapsulation**: Implemented in database models (e.g. `User.java`) using private fields and public getters/setters.
- **Polymorphism**: Used when registering WebSocket handlers through the `WebSocketConfigurer` interface, overriding standard interface methods.
- **Abstraction**: In repositories extending `MongoRepository`, which abstract away the underlying database driver operations.

26 & 27. Database Design & Injection Security
Q: How do you protect your database against Injection attacks and XSS?
Answer

- **Mongo Injection**: Using Spring Data Mongo interfaces automatically parameterizes database queries, preventing injection attacks.
- **XSS (Cross-Site Scripting)**: In `app.js`, all user-generated text is escaped using an HTML entity conversion helper function before rendering, preventing script tags from executing in users' browsers.

28 to 31. Operational concerns (Deployment, Logging, Performance)
Q: Why use SLF4J loggers instead of System.out.println? How do you improve performance?
Answer

`System.out.println` is synchronous and block thread execution. **SLF4J** logging is asynchronous, supports log levels (`INFO`, `WARN`, `ERROR`), and formats outputs efficiently. To improve database performance, I added unique indexes and enabled database connection pooling, which reuse database connection resources instead of allocating a new connection for every query.

32 & 33. Scalability & Architecture Designs
Q: How would you scale this application from 100 to 100,000 users?
Answer

I would deploy the application across multiple server instances running behind a **Load Balancer**. To sync WebSocket connections across different servers, I would integrate a **Redis Pub/Sub** message broker to broadcast messages between nodes. I would also migrate media storage to a **CDN** (Content Delivery Network) like AWS CloudFront and use **database sharding** in MongoDB Atlas to split collections across multiple cluster partitions.

34 & 35. Project-Based Design Scenarios
Q: What happens to active messages if the server restarts? Do users lose them?
Answer

No, users do not lose messages because we always persist chat logs to the MongoDB database first. If the server restarts, only active WebSocket sessions are briefly disconnected. The client-side JS automatically reconnects, and when a user selects a chat, the client requests the log history, which the server retrieves from MongoDB.

Q: How would you implement: typing indicators, read receipts, and group chats?
Answer

- **Typing Indicators**: Send a lightweight WebSocket event of type `TYPING` when a user focuses the input box. The server forwards this event to the recipient to display "User is typing...", clearing it after 3 seconds of inactivity.
- **Read Receipts**: Add a `read` boolean field to messages. When a recipient opens the chat pane, the client sends a `READ_CONFIRMATION` event to the server. The server updates the database status and sends a WebSocket event to the sender to display double ticks.
- **Group Chats**: Save a `Group` document in MongoDB with a list of member IDs. When a user sends a message to a group ID, the handler checks if they are a member, saves the message, and broadcasts it to all group members who are currently online.
