Module 1: Frontend & JavaScript Basics
Q1 What is "Vanilla JavaScript"?
Tests: Raw language understanding
Core Concept

JavaScript is the core scripting language executed by browsers. "Vanilla JavaScript" simply refers to writing plain, raw JavaScript without using external helper libraries or frameworks (such as jQuery, React, or Angular).

Ideal Interview Answer

"Vanilla JavaScript is raw, standard JavaScript code executed directly by the browser's engine. It requires no compilers or heavy external libraries, which makes the web application fast, lightweight, and ensures we have direct control over browser APIs and DOM manipulation."

Q2 What is the DOM (Document Object Model)?
Tests: Browser rendering principles
Core Concept

The browser converts HTML tags into a tree of JavaScript objects. This tree structure represents the current webpage and is called the Document Object Model.

Ideal Interview Answer

"The Document Object Model (DOM) is an object-oriented representation of the HTML document. It represents the page structure as a tree of nodes. JavaScript uses the DOM API (such as `document.getElementById`) to dynamically read, modify, add, or delete HTML elements and styles on the page in response to user actions."

Q3 What does `document.addEventListener("DOMContentLoaded", ...)` do in app.js?
Tests: Client-side lifecycle execution
Core Concept

If JavaScript executes before the HTML is fully downloaded and parsed, it won't find the target DOM nodes, causing errors. This event waits until the HTML template is completely constructed.

Ideal Interview Answer

"It is an event listener that waits until the browser has fully loaded and parsed the HTML structure of the page, without waiting for stylesheets or images to load. This ensures that all DOM elements (like inputs, buttons, and panels) exist in memory before our JavaScript code runs event bindings on them."

Q4 What is the difference between `let`, `const`, and `var` in JavaScript?
Tests: Scoping and variable declaration rules
Core Concept

`var` is function-scoped and can be reassigned. `let` and `const` are block-scoped. `const` creates a read-only reference that cannot be reassigned.

Ideal Interview Answer

"`const` is block-scoped and represents a constant reference; its value cannot be re-assigned once initialized. `let` is block-scoped and is used for variables whose values are expected to change over time. `var` is older, function-scoped, and allows variable hoisting, which can lead to bugs. We avoid using `var` in modern JavaScript."

Q5 What is localStorage, and how is it used in this project?
Tests: Browser data caching and persistence
Core Concept

Local Storage stores string data inside the user's browser with no expiration date, remaining saved even when the browser is closed or restarted.

Ideal Interview Answer

"Local Storage is a web storage API that allows websites to store key-value string pairs persistently in the user's browser. In this project, I used `localStorage.setItem` to save the user's JWT token and username upon a successful login. On page load, the app checks if a token exists; if it does, it attempts an automatic login, bypassing the connection form."

Q6 What is a FileReader, and how is it used to send images?
Tests: Binary file streaming and serialization
Core Concept

Browsers cannot write raw local file bytes directly to standard WebSocket text pipelines. The `FileReader` translates files into Base64 format, which represents binary files as a text string.

Ideal Interview Answer

"The `FileReader` object lets web applications asynchronously read the contents of files stored on the user's computer. When a user selects an image or document, `FileReader` reads it and converts it into a Base64 Data URL. This string is then packed into our JSON message payload and sent across the WebSocket channel."

Module 2: WebSockets & Protocols
Q7 What is the difference between HTTP and WebSockets? Why choose WebSockets?
Tests: Core network protocol knowledge
Core Concept

HTTP is uni-directional (request-response). WebSockets provide a stateful, bi-directional persistent connection over a single TCP connection.

Ideal Interview Answer

"HTTP requires the client to request data first, which forces inefficient techniques like long-polling to check for new messages. WebSockets establish a single, long-lived TCP connection, allowing the server to push messages to the client instantly as they arrive. This reduces packet header overhead and latency, which is essential for a real-time chat application."

Q8 What does it mean that a WebSocket is "Full-Duplex" and "Stateful"?
Tests: Socket terminology definitions
Core Concept

Full-duplex channels allow data to travel both directions simultaneously. Stateful means the socket remains open and the server maintains references to client sessions.

Ideal Interview Answer

"Full-Duplex means communication flows in both directions simultaneously over a single channel. Stateful means the connection remains open, and the server retains active information about the connection state (like who is logged in and their socket session). This contrasts with HTTP, which is stateless and closes the connection after every response."

Q9 Explain the WebSocket Handshake process.
Tests: Connection upgrade life cycle
Core Concept

The connection begins as standard HTTP but includes upgrade headers. Once approved, HTTP is bypassed and the connection switches to WebSocket protocols.

Ideal Interview Answer

"The handshake is the bridge between HTTP and WebSockets. The connection starts as a standard HTTP GET request. The client sends a header `Upgrade: websocket`. If the server accepts, it returns an HTTP 101 Switching Protocols response. The TCP connection remains open, and both parties switch to sending WebSocket data frames."

Module 3: Security & Token Authentication
Q10 What is a JWT (JSON Web Token)? Describe its structure.
Tests: Token composition and standards
Core Concept

JWT is a signed, compact JSON string consisting of three parts separated by dots: Header (metadata), Payload (data fields), and Signature (tamper verification).

Ideal Interview Answer

"A JWT is an open standard (RFC 7519) that defines a compact and self-contained way for securely transmitting information between parties as a JSON object. It consists of three parts: (1) Header (specifies the hashing algorithm), (2) Payload (contains claims like username), and (3) Signature (hash generated by combining header, payload, and a secret server key to verify token authenticity)."

Q11 What is the difference between encryption and hashing?
Tests: Cryptographic fundamentals
Core Concept

Hashing is a one-way mathematical function (cannot be unscrambled). Encryption is a two-way function (can be decrypted using a secret key).

Ideal Interview Answer

"Hashing is a one-way cryptographic function. Once data is hashed (e.g., using BCrypt), it cannot be reversed back to plain text. We hash passwords so that even if the database is leaked, raw passwords remain protected. Encryption is a two-way function; data is scrambled using a key and can be decrypted back to plain text later if the correct key is provided."

Q12 How does BCrypt work, and why is it preferred over SHA-256 for passwords?
Tests: Password protection algorithms
Core Concept

SHA-256 is fast, making it easy to brute-force if database rows are exposed. BCrypt introduces salt and a work-factor (computational delay), slowing down potential attackers.

Ideal Interview Answer

"SHA-256 is designed to be fast, which makes it vulnerable to GPU-based brute-force attacks if the database leaks. BCrypt is slow by design. It implements a configurable work factor (computational rounds) to slow down hashing, making brute-force attacks computationally impractical. Furthermore, it automatically salts each password, ensuring that two users with the same password have completely different hashes, protecting against Rainbow Table attacks."

Q13 How does the WebSocket Handshake upgrade interceptor secure the connection?
Tests: Secure handshaking design
Core Concept

We extract the token query parameter, run JWT validation, and reject connection upgrades if the token is invalid or missing, blocking unauthorized sockets immediately.

Ideal Interview Answer

"The client sends an HTTP GET request with an Upgrade header to the `/chat` endpoint, passing the JWT in the URL query parameter. Before Spring Boot upgrades the connection to a WebSocket, our custom `AuthHandshakeInterceptor` intercepts it. It validates the JWT. If the token is valid, it extracts the username, saves it into the session attributes map, and returns `true` to allow the handshake. If invalid, it returns HTTP 401 Unauthorized, blocking the connection before the WebSocket session is even allocated."

Module 4: Database (MongoDB)
Q14 Why did you choose MongoDB instead of a Relational Database (SQL)?
Tests: Database engine selection trade-offs
Core Concept

Chat applications require write-heavy, unstructured structures. JSON BSON structures mapping with WebSockets fit document-based engines without relational joins.

Ideal Interview Answer

"Chat applications are highly write-heavy and have semi-structured data schemas. A message might be simple text, or it might contain media links, file metadata, and dynamic properties. Storing this in a relational database requires nullable columns or complex table joins. MongoDB is a document-based NoSQL database that allows us to store messages as single documents. This eliminates joins, matches the JSON format of WebSockets, and allows easy horizontal scaling using sharding."

Q15 How does your private message history query work in MongoDB?
Tests: NoSQL logical filters
Core Concept

Retrieving direct chat threads requires searching for records where A sends to B or B sends to A, ordered chronologically.

Ideal Interview Answer

"In `MessageRepository.java`, I wrote a custom MongoDB query using the `$or` operator. It searches for documents where `sender` is User A and `recipient` is User B, OR `sender` is User B and `recipient` is User A. I also added a sort definition `{'timestamp': 1}` to ensure the records are returned in chronological order for the chat timeline."

Module 5: System Architecture & Scaling
Q16 Walk me through the step-by-step path of a private message from Sender to Recipient.
Tests: End-to-end trace execution mapping
Core Concept

Understanding the flow of data across frontend inputs, WebSocket frames, Spring event switch loops, database writes, and target session delivery.

Ideal Interview Answer

"First, the client inputs text, clicks Send, and JavaScript packs it as JSON of type `SEND_PRIVATE_MSG`. It is sent over the WebSocket and intercepted by `ChatWebSocketHandler`. The server immediately saves the message to MongoDB. It then looks up the recipient's name in our `nicknameToSession` map. If online, the server writes the message directly to the recipient's socket. It also sends a confirmation frame back to the sender's socket to render the chat bubble instantly."

Q17 How did you implement the "Offline Messaging" logic?
Tests: State management design
Core Concept

Decoupled socket routing from database logging. Senders write logs directly to database collections, which offline recipients pull when they connect.

Ideal Interview Answer

"When User A sends a message to User B, the server always persists the message to MongoDB first. The server then checks if User B is online. If they are offline, the server skips the socket broadcast step and sends a success confirmation only to User A. When User B logs in later, their browser requests history (`GET_HISTORY`) for their chat with User A, and the server fetches all offline messages from MongoDB and renders them."

Q18 How would you scale this chat application to support 100,000 active users?
Tests: Advanced system design & scaling
Core Concept

Single instances hold active socket references in-memory. Multi-node setups require a distributed pub-sub backplane to sync socket events.

Ideal Interview Answer

"Currently, socket sessions are stored in-memory on a single server, which limits vertical scaling. To scale horizontally, I would deploy a load balancer and spin up multiple server nodes. I would integrate a **Redis Pub/Sub** or **Kafka** message broker as a backend channel. When a message is sent, the handling node publishes it to Redis. All other server instances listen to Redis, locate the recipient if connected to their local nodes, and route the message, ensuring cross-server communication."
